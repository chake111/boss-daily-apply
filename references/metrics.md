# 指标口径：回复率怎么算才不会骗自己

> 结论先行：**别用"投了多少份"衡量效果，用"过了观察窗的回复率 + 区间"衡量。**
> 两个 40% 和 20% 的小样本在统计上分不开，拿它们比高低等于用噪音做决策。

## 旧口径错在哪

某次报表写的是「217 份，有回复 3 家，回复率 1%」。这个数不能用来做决策：

| 问题 | 表现 | 后果 |
|---|---|---|
| 分母混了两种东西 | 217 份旧投递 + N 份当天刚投的 | 刚投出去 3 小时的还没到能回复的时间，算进分母会把回复率稀释 |
| 分子只覆盖最近 40 条会话 | `reply_check.py` 只读渲染出来的会话列表 | 更早的回复永远扫不到，分子系统性偏小 |
| 公司名对不上 | 匹配失败时拿整段会话原文当公司名，写进日志的有 `09:32` 这种时间戳 | 报表拿公司名做精确比较，这些 key 永远匹配不上投递记录 |
| 没有区间 | 3/217 与 5/40 都报成一个点值 | 看不出"样本根本不够" |

最后一条最要命：**217 份里 2 家有回复，Wilson 95% 区间是 0–3%。**
也就是说「回复率 1%」和「回复率 3%」在统计上分不开，更别说拿它比较"哪个关键词值得投"。

## 新口径

| | 定义 |
|---|---|
| 分母 | 投递时间距今 ≥ **72 小时** 的记录。不足 72h 的单列「观察中」，不进分母 |
| 分子 | `reply_events.jsonl` 里能匹配到投递记录的公司（按归一后的公司名 + 最长公共子串） |
| 算回复 | 要简历 / 网申·测评 / 约面试 / 对方说话 / 系统通知（含「对方已同意」「已收到简历」） |
| 不算回复 | 已读未回、我方最后发言、拒信 |
| 匹配不上 | 记 `?<哈希>`，**不进分子**，但在待办台账里用原始会话名显示 |
| 区间 | Wilson 95%；样本 < 30 时点估计不可用 |

## 三个状态文件

| 文件 | 作用 | 谁能改 |
|---|---|---|
| `reply_events.jsonl` | 回复事件流，**只增不改**，按 (日期, 公司, 类别, 文本) 去重 | 只能 `reply_check.py` 追加 |
| `pending_actions.json` | 待办台账。会话滑出列表也不会消失，只能 `--resolve` 关闭 | 人工 `--resolve` |
| `img_mode_log.json` | 每份投递实际发的哪种图（A/B 分组依据） | 只能 `send_img2.py` 写 |

> `stream_progress.json` / `walk_state.json` 仍然只由投递流程写。指标改造没有动它们。

## 命令

```bash
python scripts/reply_check.py              # 扫一遍：更新事件流 + 待办台账
python scripts/reply_check.py --list       # 只看台账（不碰浏览器）
python scripts/reply_check.py --resolve ab12   # 标记某条已处理
python scripts/reply_check.py --dump x.json    # 存会话原文，便于离线复查
python scripts/reply_check.py --from x.json    # 用存下的原文跑，不碰浏览器

python scripts/stats.py                    # 默认 72h 观察窗 + 并入旧记录
python scripts/stats.py --window 24        # 改观察窗
python scripts/stats.py --strict           # 只算已过窗的，不要旧记录
```

## 简历图 A/B

`send_img2.py --auto-img` 的行为：

1. 按**公司名**的 md5 奇偶分桶（同一家公司永远在同一组，重发不会跨组）
2. A 组 → 查 `resume/variants.json` 按投递方向选变体 → 现场渲染 → 发送
3. A 组但该方向还没变体 → 退回通用图，记 `A:no-variant`
4. B 组 → 通用图，记 `B:generic`
5. 每组实际发了什么图写进 `img_mode_log.json`，`stats.py` 的「按简历图（A/B）」表直接读它

**读法**：先看两组的 n 是否都 ≥ 30。不到就别下结论——A/B 要跑出显著差异，
样本量得是几百份级别，不是几十份。

## 实验纪律：A/B 期间别碰招呼语

默认招呼语是和简历图并列的**第二个变量**。A/B 跑起来之后如果同时改招呼语，
两组都会受影响，最后谁也说不清是图的作用还是文案的作用。

所以顺序是：

1. 先跑 A/B（简历图），招呼语保持不动；
2. 等 B 组和 A 组的 n 都过 30、区间分得开，再决定留定制图还是退回通用图；
3. 然后才动招呼语，并且**改之前先记下当时的基线回复率**，否则又是一次无对照的改动。

## 还需要浏览器的那部分

`reply_check.py` 抓会话要连 WebBridge（`127.0.0.1:10086`）。桥没起时会直接报连接错误，
此时可以先用 `--list` 看台账、`--from` 回放上次的 dump，不影响读历史。

## 常见自我欺骗

- **把"投出去"当成"有效投递"**：分母里全是 3 小时内刚投的，回复率会低到没意义。
- **拿两组的点估计比高低**：40% vs 20% 但 n=5 vs n=10，区间大面积重叠。
- **用"会话列表里有回复"当分子**：列表只渲染 ~40 条，越早的越扫不到，分子只会偏小。
- **改了招呼语又改图，然后归因给其中一个**：两个变量同时动，实验作废。

## 定制打招呼语 vs 通用桶文案 A/B 对照纪律

- **分组依据**：`greeting_log.jsonl` 与投递台账中的 `src` 字段：
  - `src = "jd"`：Step 4 读完 JD 专属生成的定制打招呼语组；
  - `src = "direction"`：退回 `greetings.json` 四个方向桶的通用文案对照组。
- **纪律红线**：
  - 各组分母必须过窗（≥72 小时）；
  - 单组 `n < 30` 时一律标「样本不足，不作胜负比较」，避免随机噪音干扰；
  - 只有当两组样本量均 ≥30 且 Wilson 95% 区间出现显著分离时，才可确认定制话术的增益效果。
